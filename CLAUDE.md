- ClickUp api documentation is available here: https://developer.clickup.com/reference/gettasks
- Think about api limits. ClickUp allows 100 api calls per minute per user. A typical workflow must not exceed that.
- Implement caching by using a global variable and setting it to null after a setTimeout with GLOBAL_REFRESH_INTERVAL. The ClickUp Api limit resets after a minute, so we usually don't need to cache longer than a minute.
- Cache promises, not results, to prevent race conditions when multiple concurrent calls happen before the first completes (see getAllTeamMembers, getCurrentUser, getTaskSearchIndex, getSpaceSearchIndex patterns).
- Use "npm run build" to compile the typescript for validation.
- Use "npm run cli" to test mcp calls.
- CLI syntax: npm run cli <tool> key=value key2="\"quoted string\"" arrayKey='["item1","item2"]' objectKey='{"field":"value"}'
- For multi-line values (markdown descriptions/comments) call "npx ts-node src/cli.ts" directly - "npm run cli" re-splits arguments through a second shell and loses them.
- Use "npm run test" to run tests.
- Use "npm run smoke" after a build to check the MCP protocol layer (initialize, tools/list, schemas) - "npm run cli" calls tool callbacks directly and never exercises stdio transport or tool registration. Add "-- <task_id> <image.png>" to also post a real comment with an image.
- Tests need src/tests/setup.ts preloaded (see the test script): it points global fetch at the npm undici so MockAgent can intercept. Node's built-in fetch uses Node's own bundled undici, which MockAgent cannot reach.
- Use console.error to prevent writing log messages to stdout.
- MCPB manifest.json spec is at https://github.com/anthropics/mcpb/blob/main/README.md - update tools section when adding new MCP tools.
- Update the CHANGELOG.md when changing or implementing a new feature.
- Backwards compatibility does not matter, an LLM will understand new parameters.
- Mention ID's, not just names, when outputting references. for example "User: Username (user_id: 12345)"
- `PUT /api/v2/comment/{id}` accepts the same undocumented rich `comment` fragment array as comment creation (the API reference only lists `comment_text`, and `assignee`/`resolved` are not actually required). Sending `comment` and `comment_text` together appends the latter. There is no `GET /comment/{id}`, so editComment reads the task's comment list to check author and age. That list returns only the 25 newest comments per page - `start_date` is not a real parameter and is ignored; older pages need `start` + `start_id` of the previous page's last comment.
- ClickUp comments cannot render tables (no table fragment exists; unknown attributes are stored but render as plain text) - convertMarkdownToClickUpBlocks turns tables into aligned pipe tables inside a code block. Quill block attributes apply per line: every code-block line needs its own `\n` fragment with the code-block attribute, otherwise only the last line renders as code. Comments DO support strike/underline/color attributes even though the comment UI barely exposes them.
- Image writing lives in src/shared/attachments.ts: markdown image sources are uploaded to the task, then comments get a `type: "image"` fragment carrying the *whole* attachment object (a bare URL string renders as an empty tile), while descriptions only need the markdown URL swapped. Attachments always belong to a task - doc pages cannot have them. Reading renders images back as `![alt](url)` markdown (clickup-text.ts `toMarkdownImage`) so a comment read via getTaskById can be fed straight back into editComment without losing them - keep that read/write symmetry intact.
- Typed comment segments on read (clickup-text.ts `renderTypedSegment`): `tag` (user mention) renders `@Name (user_id: N)`, `emoticon` its emoji, and any other typed segment (or untyped one without text) gets a bounded search (depth 3; order: preferred keys `url`/`link`/`href`/`src`/`source` in the segment, then in its `data-attachment` JSON, then any http(s) string in the segment, then in `data-attachment`; the any-URL passes skip the nested `user` object and avatar/profile/picture/thumbnail/icon keys) and renders `[label](url)`; with no URL it keeps its text, or - with empty/missing text - a bounded summary `[type segment: k=v ... (+N fields omitted)]` appended in place (6 scalar fields, 80-char values, 300 chars total, never token/secret/key/password/auth/email fields or `data:` URIs; never a raw JSON dump). The mention name is username, else segment text, else `unknown` (never the e-mail), with `@` and an embedded `(user_id:` neutralised and capped at 100 chars so it always matches `USER_MENTION_PATTERN`. Only `tag`, `emoticon` and `attributes.link` follow ClickUp's documented comment formatting - the `bookmark`/`attachment`/`frame`/`link_mention` shapes are assumed, not captured. The writer turns `@Name (user_id: N)` in plain markdown text (not inline code, code blocks or link text) back into `{type: "tag", user: {id: N}}` so a read comment still round-trips through editComment. Literal text must never become a live tag (it would notify someone): the writer honours `\@Name (user_id: N)` (it checks the text node's `position` offsets against the markdown source, because remark strips the backslash from the node value), and the reader escapes the `@` of any plain text matching the pattern (not in link labels, inline code or code-block lines).
- ClickUp comments have no paragraph margins: a paragraph break is an extra empty `\n` fragment (Enter twice in the UI). convertMarkdownToClickUpBlocks inserts one between adjacent paragraphs/lists only - headings, code blocks and blockquotes already render with their own spacing.

## Verifying a change (agent-ready standard)

- `just test` is CI's unit suite (ClickUp mocked, no secret); `just build` compiles; `just smoke` is the stdio protocol smoke (needs a token in `.env`).
- The verify skill, `.claude/skills/verify-clickup-mcp/`, is the one place that says how to bring the hosted server up with throwaway values (`launch.sh`), check it (`doctor.sh`, `just doctor`), drive it and save proof under `.verify/evidence/<date>/` (`drive.sh all`, `--live` for stdio tool calls with `CLICKUP_API_KEY`), then clean up. `just verify` runs the four in order. Its `features/` map lists the tool groups and their gotchas. Run it before opening a PR; `/verify` does this for you.
- A PR body follows `.github/PULL_REQUEST_TEMPLATE.md`: why, what it leaves out, what it could break, how it was proved. A PR without the fourth section is a draft; "tests pass" without the output does not count.
- Secrets: a gitignored `.env` locally (no Doppler project); the Railway service `clickup-mcp` (MCPs project) holds its own. Never print one.
